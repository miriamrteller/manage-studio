## PDF content

Business name and logo (PNG/JPEG fetched from `tenants.logo_url`, best effort),
contract title (template name), shoot details (client, date, package, location,
price — the same merge values the client saw), the exact `wording_snapshot`, and a
signature block: typed name, signed-at in Asia/Jerusalem, signer email, method,
template version, evidence id and `consent_version_hash`. Footer: business name,
page x of y, evidence id. A4, labels in the tenant language.

## Hebrew

pdf-lib does no bidi, and fontkit (which pdf-lib uses to encode text) *reverses* any
string whose first strong character is right-to-left. So:

1. Text is wrapped in logical order, then each line is reordered into visual order
   with bidi-js (UAX #9: embedding levels, L1 trailing whitespace, L2 reversal,
   bracket mirroring — bidi-js's `getMirroredCharactersMap` takes the `levels`
   array, not the result object its README shows).
2. Each visual line is split into runs; Hebrew-script runs are handed to pdf-lib in
   logical order so fontkit's own reversal yields the visual order, and all other
   runs are drawn as is, left to right, at computed x positions.
3. Paragraph direction is detected per paragraph (first strong character), so a
   Hebrew clause inside an English contract stays right-to-left and vice versa;
   RTL paragraphs are right-aligned.
4. Alef (SIL OFL 1.1) covers Hebrew (incl. niqqud), Latin, ₪ and punctuation in one
   face, embedded as a subset; no runtime font download.

Verified by rendering Hebrew and English samples (with and without a logo) and
rasterising them with `pdftoppm`: Hebrew words read correctly right-to-left,
numbers and Latin fragments stay left-to-right inside Hebrew lines, brackets and
quotes enclose their content, mixed paragraphs align by their own direction.

## Evidence hash — decision

`record_hmac` already seals `pdf_sha256` as one of its 15 canonical fields. For job
contracts the PDF is rendered, hashed and uploaded **before** `sign_waiver()`, so the
sealed `pdf_sha256` is the SHA-256 of the stored file; `pdf_storage_path` is the
object key. The canonical form is unchanged (same 15 fields, same ordering, same
serialisation — now built by `waiverRecordCanonical()` and still pinned from the
signer source by `apps/web/src/__tests__/waiver-evidence-verify.test.ts`), so
`verify-waiver-evidence.ts` is untouched and verifies new rows as before; a
changed hash fails verification (`evidence.test.ts`). Dance rows keep the sentinels
and verify exactly as today. The PDF itself carries the evidence id and
`consent_version_hash` (it cannot contain `record_hmac`, which is computed over it).

Failure policy (changed in review): a render or storage failure must never block
a client from signing a legal contract. `prepareWaiverPdf` then returns the same
sentinel pair a dance waiver stores (the verifier accepts it unchanged) with a
`failure` reason; signing proceeds, `recordContractPdfFailure` writes an
`audit_log` row (`job_contract_pdf_failed`) and sets
`job_details.contract_pdf_pending`, and the emails still go out with links to the
client portal / admin shoot page instead of the PDF. The admin shoot page then
shows "Generate PDF" (`job-contract-pdf-generate`, tenant admin only): it renders
from the sealed `wording_snapshot` (plus the job's current details for the header),
stores the PDF under its own key and records it in `waiver_evidence_pdfs` —
never on the immutable evidence row, so the sealed record is untouched. Such a PDF
is documented, in the table and inside the PDF itself, as *generated after signing*:
it reproduces the sealed wording but its own hash is not part of `record_hmac`.
A second click reuses the generated PDF. `job-contract-pdf-link` serves the sealed
PDF first, else the generated one.

A retry or double submit first looks the key up and reuses the stored row — no
second render, no orphaned object. A truly concurrent pair can leave one orphan
object (logged); the sealed row always points at its own file.

## Emails

Both the signer (`signed_by_email`, else the job's client email) and the studio
(`tenants.contact_email`), in the tenant language, from the tenant sender
(`resolveTenantSender`). Idempotent through `claim_automatic_email` /
`complete_automatic_email` keyed by engagement (unique per key), so a retry sends
nothing twice and a failed send is retried up to three times. The PDF is attached on
Resend; the Cloudflare Email Sending REST path is not known to take attachments, so
there the body carries the link only. Every email has a download link: a 72-hour
signed URL, falling back to the client portal / admin shoot page when storage
cannot sign one. Not toggleable in the automatic-email settings on purpose.

## Access

`job-contract-pdf-link` (session required) loads the job, then
`decideContractPdfAccess`: tenant admin of the job's tenant, or the person on the
job / a member of its client account. Anyone else gets 404 (no probing); unsigned
or pre-Thread-G rows get 409. Returns a 10-minute signed URL with a download
filename and writes an `audit_log` row. The bucket stays private; the existing
storage RLS is unchanged.
